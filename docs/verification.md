# 验证记录

日期：2026-11-13，Windows x64，当前版本 1.3.0。所有认证用例均使用虚构凭据与本地服务，未读取真实用户密码或财务系统登录数据。

## 1.3.0 轻量版

- 原生助手使用系统 DLL，无随包 Node、.NET 或 VC++ DLL。编译保留 DEP/ASLR，发行副本由锁定版本的 Terser 压缩；源码包不含运行时与浏览器配置。
- 单次助手测试先对旧版观察到不主动退出，再用新版通过。测试还覆盖无关站点 Cookie、不同源页面存储、分区 Cookie、非法映射与已停用的转发命令。
- `tests/release-browser.ps1` 使用实际压缩扩展和原生助手通过界面、A/B 登录隔离、HttpOnly Cookie 和两类存储、中文数据、导入只执行一次及已打开时的提示。另用最终发行助手验证普通窗口复用原格式资料目录并打开 Chrome 同步设置；未实际登录 Google。
- 验收只关闭专属测试窗口，临时调试已解除，恢复了验收前的本机助手注册。
- 旧助手实测工作集合计约 59 MiB、私有内存约 34 MiB。新版普通命令返回后无助手进程；导入登录后的等待进程实测工作集约 9.2 MiB、私有内存约 1.5 MiB。以上都不含 Chrome 自身。新助手为 143,872 字节，扩展文件由 29,848 字节降至 23,417 字节。

## 双网页退出的复现与修正

`tests/login-isolation-browser.mjs` 以同一域名的两个 IP 分别运行认证服务 A/B：A 的凭据由 B 返回 401 并清理 Cookie，页面清理 localStorage，另一标签收到存储变化后退出。

旧 1.1.0 的 start 真实入口在浏览器中得到 `[false, false]`（两页均已退出），回归按预期失败。1.2.0 删除标签切换界面及持续拦截，在后台拒绝旧 start 消息。相同用例得到两个原网页均保持登录，地址、Cookie、localStorage 未改动。

同一回归还以本机 Google Chrome 启动两个真实独立配置，分别固定到 A/B，使用各自凭据登录。清理 B 的 Cookie 和 localStorage 后，B 退出，A 和原 Chrome 中两个网页仍保持登录。结果在 `output/playwright/login-isolation-results.json`。

这项修正是停用不具备登录隔离的旧入口，采用独立配置窗口；并不声称实现了 Chrome 同窗口逐标签登录隔离。

## 安装及历史说明

此前 AppData 别名被打包应用重定向至应用私有目录，造成 Explorer 位置不可用。安装已改为在普通解压目录原地注册，F 盘路径通过文件句柄核验。安装脚本本次未变，复用 `tests/install-smoke.ps1` 的真实注册回归证据。

1.0.0 / 1.1.0 曾验证标签请求可以分别命中两个 IP，同时也验证过 Cookie 共享；那些路由结果不能作为登录隔离的证据。当前 start 流程已不可启用，旧标签模式的缓存、Worker 和外部断开行为不再作为当前产品能力。

## 未执行项与限制

- 未登录截图中的财务系统，没有执行财务写入；真实两个 IP 的业务兼容性需用户验收。
- 未登录用户 Google 账户或验证其云端同步；密码、书签及自动填充需用户在环境窗口本人登录 Chrome 同步。
- 独立浏览器存储不能改变服务器单点登录、共享会话撤销或其他服务端规则。服务器不接受源登录、分区 Cookie、设备绑定登录和 IndexedDB 等情况仍可能要求重新登录。
- 已被清理或已失效的登录不能恢复。升级前需停止旧接管或关闭旧业务标签，再由用户在扩展管理页重新加载；不能把磁盘文件更新当作用户当前浏览器已经重载。
